## 1. Problem Statement

`VAL-CAP-004` is the MVP-smoke must-pass row for "1080p60 NVENC monitor capture, 60 s recording, drop ≤ 0.1 % and cadence within ±0.5 % of 60 fps." During T-021 rerun 3 on the M1 host (NVIDIA RTX 4080 SUPER, KDE Plasma Wayland + xdg-desktop-portal-kde, 4K monitor):

- The portal/PipeWire negotiation delivered `XR24 3840×2160 fps_num=0 fps_den=1` — i.e., the monitor's **native 4K resolution at variable framerate**, not the row's declared 1080p60 workload.
- Diagnostics observed ~105 fps mean (`observedFps` ranged 102–106 across 61 samples).
- `encoder.probeResult` reported both `nvenc` and `libx264` as `not-implemented-yet { follow_up_ticket: "T-017a" }`. `encoder.selected` was therefore never emitted.

ISS-001 has been resolved: the harness no longer treats `fps_num=0` as a `0 fps` band, and the row's declared `nominalFps: 60` is used as the cadence target when the portal returns variable-rate. ISS-002 remains open and is independent (encoder backend implementation).

The remaining defect — ISS-003 — is the **workload mismatch** itself: the row's declared cell (1920×1080@60) does not match the negotiated cell (3840×2160@variable). The row currently fails honestly (105 fps ≠ 60 fps band), but it fails for the *wrong stated reason*: the gate name reads "cadence mean within ±0.5 % of 60 fps", which papers over the more fundamental fact that **the host did not deliver the row's declared capture cell at all**. The next implementation pass needs the design call on how the helper, portal, and validation should jointly handle "the host delivers a different cell than the row declared."

## 3. Current Code Facts

All references are to the **base commit** `78ce77c`. No source file is modified by this handover.

### Helper — `helper/src/capture/pipewire.rs`

- `build_format_enum_pod()` (around L372–423) emits a **static** `ParamType::EnumFormat` pod via `pipewire::spa::pod::object!(...)`. `FormatProperties::VideoSize` uses `Choice::Range` with `default = Rectangle { width: 1920, height: 1080 }`, `min = 1×1`, `max = 8192×4320`. `FormatProperties::VideoFramerate` defaults to `Fraction { num: 0, den: 1 }` (variable-rate). These are **defaults that the compositor may freely override**, not hard constraints. There is no per-session parameterization of this pod.
- `capture.requestSession` (around L1980–2010) receives `RequestSessionOpts` from the JSON-RPC client but **does not** thread resolution/fps hints into the pod builder.
- `capture.startStream` (around L2012–2032) calls `c.start_stream()` with no extra format parameters.
- `set_region` (around L1067–1074) and `set_framerate_hint` (around L1076–1083) are stubs marked `TODO T-016a` (forward to PW stream crop/scale params; forward to encoder framerate hint). Neither currently affects negotiation or the encoded output.

### Helper — `helper/src/encoder/`

- `EncoderBackend` trait (`backend.rs`) defines `probe(&CaptureFormat) → ProbeOutcome`, `configure(&mut, EncoderConfig)`, `init_segment()`, `push_frame(FrameHandle)`, `drain()`, `teardown()`.
- `EncoderConfig` carries `format: CaptureFormat`, `target_bitrate_bps`, `gop_seconds`. There is **no `encoderOutputFormat`** distinct from the captured format. Whatever the capture layer negotiates is what the encoder is configured against.
- `mod.rs::run_session` constructs `EncoderSelectedEvent` (around L134–145) with `parameters = { stream_id, width: format.width, height: format.height, fps_num: format.fps_num, fps_den: format.fps_den, fourcc }` — directly mirroring the captured format.
- `backends/nvenc.rs` and `backends/x264.rs` both return `ProbeOutcome::Unavailable { reason: "not-implemented-yet", follow_up_ticket: "T-017a" }`. Neither implements `configure`, `push_frame`, `drain`, or `teardown` beyond `EncoderError::NotImplementedYet`.

### Validation — `validation/rows.ts`, `validation/drivers.ts`, `validation/types.ts`, `validation/assertions.ts`

- `SmokeRow` (`rows.ts`) has fields `id, title, classification, tier, ownerOnFail, smokeOrder, linkedSourceCase, budgetMs, nominalFps?: number`. **There is no `expectedResolution`, `expectedCaptureFormat`, or `expectedEncoderBackend` field.** The row's declared workload is encoded only in its title string ("1080p60 NVENC monitor capture") and its `nominalFps`.
- `driveValCap004` (`drivers.ts` L727+) reads `captureFormat` from `sessionReady.params.format`, then calls `deriveThresholdKey(captureFormat, "nvenc")`. `deriveThresholdKey` keys the drop-tier on the **captured** height: `height ≥ 2160 → "4k60-nvenc"`, `height ≥ 1440 → "1440p60-nvenc"`, else `"1080p60-nvenc"`. The row's declared cell is **not** consulted for tier selection.
- The encoder gate is strict equality on the `nvenc` backend name: `name: "encoder.selected backend is nvenc"`, `passed: encoderBackend === "nvenc"`. When `encoder.selected` is not emitted (ISS-002), this gate fails with `observed: "(not received)"`.
- `nominalFps` (ISS-001) supplies the cadence target when the negotiated format is variable-rate. The cadence gate band is `±cadenceMeanToleranceFrac × nominalFps`.

## 4. D1–D4 Comparison

### D1 — Constrain PipeWire `EnumFormat` to fixed 1920×1080@60

**Approach.** Replace `Choice::Range`/`Choice::None` defaults in `build_format_enum_pod()` with hard constraints at `1920×1080` and `60/1`, either statically or by parameterizing the pod builder via `RequestSessionOpts`. The portal/compositor is then asked to deliver exactly that cell or fail negotiation.

| Dim | Value |
|---|---|
| Pros | Row title and negotiated cell would match by construction when negotiation succeeds. Cadence target trivially derives from negotiated fps. |
| Cons | **Violates N-003**: "Source-native resolution accepted as-is. No capture-layer scaling or letterboxing. Framerate hints: advisory only." A hard pod constraint is the opposite of "advisory." Most compositors (Mutter, KWin) will refuse to scale and either negotiate native-only or return `format-renegotiation-failed`/`no-acceptable-buffer-type`. The 1440p60 and 4K60 must-pass cells in N-008 §18 then become impossible to exercise — the same pod cannot constrain to multiple cells. Per-session reparameterization is a non-trivial helper refactor. |
| Code surface | `helper/src/capture/pipewire.rs` (parameterize pod builder; thread hints from `requestSession` through to `connect`); `helper/src/protocol/types.rs` (extend `RequestSessionOpts`); validation harness to pass hints. Multi-file Rust. |
| Risk | High. Breaks N-003 invariant; risks deadlocking the 1440p/4K cells; portal behavior is compositor-specific. |
| Impact on ISS-002 | None. Encoder backends still not implemented. |
| Impact on T-021 rerun 4 | Still RED until ISS-002 lands. After ISS-002, may PASS on hosts whose compositor honors the constraint; FAIL with `no-acceptable-buffer-type` on hosts that do not. |

**Rejected.** Conflicts with the locked T-004/N-003 boundary, blocks future matrix cells, and shifts negotiation policy in a way that downstream rows cannot easily override.

### D2 — Accept native negotiated capture and downscale at the encoder boundary

**Approach.** Capture layer accepts whatever the compositor delivers (per N-003). Encoder layer gains a scale step (CUDA/NVENC `nvscale` or sws_scale for libx264) that converts captured frames to a row-declared `encoderOutputFormat` (e.g., 1920×1080@60). `EncoderSelectedEvent` already has slots for `encoderInputRect` and `encoderOutputFormat` in the N-007 design.

| Dim | Value |
|---|---|
| Pros | Row outcome is independent of monitor cell. Future "always export at 1080p60" product modes drop in cleanly. |
| Cons | Largest code surface of any path. New `EncoderConfig` fields. New failure surface (scale-pipeline init, GPU memory pressure, modifier compatibility for downscale on DMA-BUF). N-003 says "Capture layer never synthesises duplicate frames" — implicit fps clamp at the encoder (drop-or-duplicate to land 60 fps from a 105 fps source) re-introduces the exact v1.1.0 fake-60fps failure mode. v2.0.0 must not regress that. Variable-rate compositor output still needs a cadence policy at the encoder boundary; that policy is not free. |
| Code surface | `helper/src/encoder/backend.rs`, `mod.rs`, `backends/nvenc.rs`, `backends/x264.rs`; new scale module; `validation/drivers.ts` to assert both input and output formats. Multi-file Rust + TS. |
| Risk | High. Re-opens the fake-60fps regression surface explicitly killed in v1.1.0. Largest blast radius for the smallest validation problem. |
| Impact on ISS-002 | Strict superset of T-017a scope — adds downscale and fps clamp to backends that don't yet exist. Slows ISS-002 unblock. |
| Impact on T-021 rerun 4 | Blocked until both T-017a and the downscale path land. |

**Rejected.** N-003 and N-008 explicitly avoid capture-layer mode coercion to prevent the v1.1.0 fake-frame regression. Re-introducing a frame-rate clamp at the encoder boundary recreates that failure mode under a new name. The validation problem does not justify this scope.

### D3 — Rescope validation to the negotiated matrix cell and split/adjust rows (CHOSEN)

**Approach.** Treat the workload mismatch as a **validation-layer** defect, not a capture-layer defect. The row schema is extended (additively, mirroring the ISS-001 pattern) so each row declares the cell it expects. The runner asserts the negotiated cell matches the declared cell. Mismatch surfaces as a precise per-row failure (or a skip-with-reason gated by N-008 §18's "only cells the hardware can deliver"). The capture layer keeps its N-003 source-native semantics. The encoder keeps its no-downscale semantics. The matrix per N-008 §18 is the place that decides per-machine which cells run.

| Dim | Value |
|---|---|
| Pros | Aligned with N-003 ("source-native accepted as-is"). Aligned with N-008 §18 (per-cell rows; per-machine coverage gate). Additive schema change (same pattern as ISS-001's `nominalFps`). No Rust change. No downscale, no fps clamp, no fake-60fps regression risk. Workload mismatch becomes **explicitly visible** in the per-row report — never hidden, never silently passed. Independent of ISS-002 critical path. |
| Cons | Requires a row schema change (`expectedCaptureFormat`, `expectedEncoderBackend`). The matrix gate has to know what the host delivers before deciding which rows to exercise — N-008 §18 already says this in spec; D3 adds the runtime mechanism. The current M1 host (4K monitor) does not deliver 1080p60, so VAL-CAP-004 on this host either FAILs with a clean reason or SKIPs with `host-does-not-deliver-declared-cell`. To get a green smoke signal on this host, either (a) connect a 1080p60 display, or (b) add a sibling row `VAL-CAP-004-native` that declares the host's actual cell. |
| Code surface | `validation/rows.ts` (add `expectedCaptureFormat?: { width, height }`, `expectedEncoderBackend?: string`); `validation/drivers.ts::driveValCap004` (assert negotiated.width/height equals declared; key `deriveThresholdKey` off the **declared** cell, not negotiated; emit a `host-does-not-deliver-declared-cell` skip when configured to do so). Optionally `validation/types.ts` if a new threshold-source enum is added. **No** helper, electron, src/, packaging, Cargo, or workflow change. |
| Risk | Medium. Schema change must remain additive (drivers that ignore the field are unaffected, per ISS-001 precedent). Matrix-gate semantics (skip-vs-fail policy) need to be locked in the implementation handover. |
| Impact on ISS-002 | None — strictly orthogonal. ISS-002 remains the T-017a unblock for `encoder.selected`. The encoder gate stays as-is; D3 only changes capture-cell semantics. |
| Impact on T-021 rerun 4 | After ISS-002 lands (encoder selection emits `nvenc`) AND D3 implementation lands AND the host delivers the declared cell (or the row's host-policy is set to skip), VAL-CAP-004 reaches a real green. On a 4K-only host, the green comes from the sibling row that declares the host's actual cell; VAL-CAP-004 itself skips with `host-does-not-deliver-declared-cell`. |

### D4 — Keep VAL-CAP-004 as-is and declare a 1080p60 hardware prerequisite

**Approach.** No schema change. Operator must run T-021 smoke on a host whose monitor natively delivers 1920×1080@60 fixed-rate. M1's 4K monitor is declared out-of-spec for the smoke pass.

| Dim | Value |
|---|---|
| Pros | Zero code change. |
| Cons | Hidden runtime trap: every operator on a non-1080p60 native monitor hits a confusing fail until they read the prerequisite. Many Wayland compositors deliver variable-rate (`fps_num=0`) regardless of monitor refresh — even a 1080p monitor may negotiate variable-rate, so the "prerequisite" doesn't fully eliminate the cadence-variability problem. The matrix gate's per-machine cell coverage is not encoded — the prerequisite is documentation only. |
| Code surface | Documentation only (this handover, T-021 description). |
| Risk | Low operationally; high politically — sidesteps the real defect rather than addressing it. |
| Impact on ISS-002 | None. |
| Impact on T-021 rerun 4 | Indefinitely blocked unless a 1080p60-native monitor is wired to M1. Does not generalize to M2/M3/M4 hosts whose cells differ. |

**Rejected.** D4 trades an implementation problem for an environmental constraint that the project cannot enforce. It does not make workload mismatch visible in the per-row report; it just makes mismatch a setup mistake the operator is presumed to avoid.

## 5. Chosen Path

**D3 — Rescope validation to the negotiated matrix cell and split/adjust rows.**

Per D3, the row schema gains additive fields declaring the cell each row expects; the driver asserts the negotiated cell against the declared cell; the matrix gate (N-008 §18) is the place that decides per-host which rows are exercised vs skipped. No capture-layer or encoder-layer code change.

## 6. Rejected Paths and Reasons

- **D1** — Conflicts with N-003 ("source-native; framerate hints advisory; no capture-layer scaling"). Cannot serve the 1440p60 and 4K60 must-pass cells in N-008 §18. Compositor-dependent failure mode (`no-acceptable-buffer-type`). Multi-file helper refactor for the smallest signal change.
- **D2** — Re-introduces the fake-60fps regression surface that v1.1.0 was killed for (any fps clamp at the encoder boundary is implicit drop-or-duplicate). N-003 forbids capture-layer mode synthesis; pushing it to the encoder is the same regression by a different name. Largest blast radius; strict superset of T-017a.
- **D4** — Documentation-only sidestep. Doesn't generalize across the matrix and doesn't surface workload mismatch in the per-row report. Hidden operator trap.

## 7. Updated Interpretation of VAL-CAP-004

Under D3, `VAL-CAP-004` is interpreted as follows (binding for the implementation pass):

| Aspect | Interpretation |
|---|---|
| Input capture resolution/fps expectation | The row declares `expectedCaptureFormat: { width: 1920, height: 1080 }` and `nominalFps: 60`. The negotiated `sessionReady.format` **must** match the declared `width × height` exactly. Fps is asserted against `nominalFps` per ISS-001's three-source resolution (`negotiated` → `row-config` → `missing`). |
| Encoded output resolution/fps expectation | Identical to capture. No downscale, no fps clamp. Encoded output cell equals captured cell. |
| Negotiated display mode handling | If the negotiated cell does **not** match the declared cell, the row records a precise `ThresholdResult { name: "capture cell matches declared (1920x1080)", observed: "<negotiated WxH>", required: "1920x1080", passed: false }` and the row fails. The row never silently passes on a different cell. Optional host-policy field (`onCellMismatch: "fail" | "skip"`) controls whether the runner records this as a hard fail or as a `skip-reason: "host-does-not-deliver-declared-cell"` to match N-008 §18's "only cells the hardware can deliver." Default policy = `fail`. |
| Threshold key behavior | `deriveThresholdKey` is keyed off the **declared** `expectedCaptureFormat`, not the negotiated `captureFormat`. The drop-tier (`1080p60-nvenc`) reflects the row's intent, even if the cell-match gate later fails. `thresholds.json` additively records both `expectedCaptureFormat` and `captureFormat` so the mismatch is preserved in the evidence bundle. |
| Encoder backend requirement | The row declares `expectedEncoderBackend: "nvenc"`. The encoder gate stays strict equality (`encoder.selected.backend === "nvenc"`). ISS-002 still gates this — until T-017a lands, the gate is `observed: "(not received)"` and the row fails for that independent reason. |

The `nominalFps` source-tracking from ISS-001 is preserved verbatim. The cadence band still fails honestly against `nominalFps` when the compositor returns variable-rate output that diverges from declared fps; D3 does not silence that signal.

## 9. T-017a Stub Decision

**Decision: do not create `.story/tickets/T-017a.json` in this design pass.**

Reasoning:

1. **T-017a is the ISS-002 ticket, not the ISS-003 ticket.** ISS-002 references T-017a as `follow_up_ticket` and the helper encoder stubs reference T-017a in code comments and probe-result payloads. T-017a's scope is "implement NVENC + libx264 encoder backends per N-004 / T-017 description." That is not the ISS-003 implementation target — D3's implementation target is a validation-layer rescope.
2. The prompt instructs T-017a stub creation only when "the chosen design requires T-017a as the next implementation target." Under D3, ISS-003 is unblocked without T-017a; T-017a is needed for ISS-002 along an orthogonal axis.
3. Creating a T-017a stub during a design-pass on ISS-003 would conflate two issues. T-017a should be created by the ISS-002 implementation handover, where its full T-017-derived scope can be cleanly inherited.
4. **Gap documented:** there is currently no `.story/tickets/T-017a.json` file even though code stubs and ISS-002 reference it. The next ISS-002 implementation pass should create it with `parent: T-017` (following the T-010a..e precedent), `blockedBy: []`, `description` derived from the deferred VAAPI/QSV/AMF + the "real backends instead of stubs" half of T-017's acceptance criteria. This gap is recorded here for the operator and for the next pass.

If, during the ISS-003 implementation pass, the implementer decides D3 needs to file a sibling row or a new ticket to track the matrix-gate per-host policy, they may create **T-021a** at that time. T-021a is not created in this design pass either, because its scope (which is the topic of this handover) is what the implementation pass itself encodes — pre-creating the ticket would lock the wording before the implementer reads this design.
