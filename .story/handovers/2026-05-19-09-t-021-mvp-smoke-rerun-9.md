## Root-Cause Hypothesis (no source changes made; not path-level proven by captured evidence)

The captured rerun-9 evidence proves the symptom — `capture.startStream` returned `{code:"not-implemented", message:"no-acceptable-buffer-type"}` — but does not include helper/PipeWire logs that would identify which negotiation path inside the helper produced the terminal reason. The runner harness writes JSON-RPC responses to `VAL-CAP-004/`, not helper stderr. So the analysis below is a **hypothesis** scoped to the change window, not a confirmed path-level diagnosis.

Bisect window: between rerun 8 (commit 814034f, sessionReady reached, 60 diag samples) and rerun 9 (commit b5db18b, sessionReady never reached on the same host/compositor/GPU/portal/display-mode/VRR config), the only modified file is `helper/src/capture/pipewire.rs` per `git show --stat b5db18b` (225 lines changed, +213/-12). The T-016a diff in that file:

- Rewrote `build_format_enum_pod` to accept `framerate_hint: Option<u32>` and emit a format pod whose default rate is the clamped hint (1..=240), with a range spanning 1/1..=240/1.
- Added a `PwCommand::UpdateFramerate(u32)` variant and a live framerate-hint shared `AtomicU32` on `DiagCounters`.

The reason constant `REASON_NO_ACCEPTABLE_BUFFER_TYPE` is the canonical terminal failure path for stream negotiation in the same file; on this run it propagates through `pw_event_loop` → `capture.sessionLost` and back through the dispatcher's `start_stream().await?` → `Err(e)` arm, which wraps any `start_stream` error as `RpcError { code: String("not-implemented"), message: e.to_string(), ... }` regardless of the underlying cause. The wire-format `not-implemented` code on the response is the dispatcher's generic envelope — it is NOT evidence that T-016a left a stub in place.

What the evidence proves directly:

- `capture.requestSession` returned `{ok: true}` (portal accepted).
- `capture.startStream` failed with `no-acceptable-buffer-type` within 5197 ms.
- No `capture.sessionReady` notification was emitted.
- The pre-T-016a build on the same host reached `sessionReady`.

What the evidence does **not** prove without helper logs:

- Whether the failure came from the primary nonzero-rate format pod, a legacy fallback pod, DMA-BUF negotiation, the SHM fallback path, or a later buffer-type negotiation step.
- Whether the `UpdateFramerate` PW command interacted with the negotiation at all.
- Whether a non-PipeWire factor (e.g., compositor restart between reruns 8 and 9, KDE state) contributed.

Recommended follow-up to convert this hypothesis to a path-level diagnosis: re-run with helper stderr captured (or run the helper standalone with `RUST_LOG=debug` and replay the JSON-RPC sequence) so the `pw_event_loop` `warn!(... %reason, "PW fatal: {msg}")` line is recorded alongside the JSON-RPC response.
