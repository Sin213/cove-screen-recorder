## What was decided

T-010 was a single chore covering "everything between a green validation matrix and a published v2.0.0 tag." That is too broad to execute in one ticket. Split into five children, each scoped to a single owner-on-fail layer per N-008 §3 and a single slice of the §24 release-gate checklist. T-010 itself is now an umbrella (no execution); it closes when the five children close.

### Dependency graph

```
T-010a ─┐
T-010b ─┼─→ T-010c ─┐
                   ├─→ T-010e
T-010d ────────────┘
```

- T-010a, T-010b, T-010d run in parallel.
- T-010c blocks on T-010a + T-010b (it consumes the runner and the loads).
- T-010e blocks on T-010c + T-010d (it gates on the matrix verdict AND the packaging verdict AND explicit user approval).

### Why this split

- **T-010a (runner harness)** is the longest-lead pure-software item. It has no hardware-matrix dependency; M1 suffices for development. Its output (per-row JSON report) is the contract two downstream tickets consume.
- **T-010b (synthetic loads)** is content production. The L-MOTION-60 PTS-in-pixel frame counter is load-bearing for the no-fake-duplicated-frames check (N-008 §6.1, VAL-EXP-010, VAL-REG-002). Splitting it off lets a different implementer work in parallel without touching JSON-RPC plumbing.
- **T-010c (execution + report)** is the wall-clock-heavy ticket. Smoke ≤ 30 min on M1; RC 4–6 h on M1+M2+M3+M4 dominated by 15-min soak rows. It is also the ticket that produces the v1.1.0 vs v2.0.0 comparison plot (N-008 §21).
- **T-010d (packaging audit)** is independent of the matrix and can be done by anyone with the build machine. It is the cleanest single-machine ticket. It owns §24 items 8–9 (.sha256 sidecars + Linux .deb Depends + dependency probe).
- **T-010e (publish)** is the only ticket that touches version bumps, CHANGELOG, tags, push, publish. Per CLAUDE.md, every action in this ticket requires explicit user approval. Hard gate: both T-010c and T-010d must be green.

## Recommended first implementation ticket

**T-010a — runner harness.**

Reasons:
- Unblocked (no `blockedBy`).
- Scope is bounded by already-locked contracts: N-007 §§1–5 (IPC transport, method namespace, event surface), N-008 §6 (universal pass/fail thresholds), N-008 §7 (evidence bundle), N-008 §20 (ffprobe/mediainfo recipes), N-008 §22 (smoke suite ordering).
- Produces a stable, downstream-consumable artefact (per-row JSON report) that two other tickets need.
- Does not require hardware beyond M1.
- A Sonnet implementation session can use the lock-step plan: open socket → drive a single row end-to-end (recommend VAL-CAP-004, the 1080p60 NVENC 60 s L-MOTION-60 row) → emit a report → expand to all 18 smoke rows.

**T-010b** is the second-best first pick if the implementer prefers content production over RPC plumbing — also unblocked and parallelisable.

**T-010d** is the third option if the implementer prefers no ffmpeg/PipeWire work — also unblocked, smallest in scope, single-machine.
