## 15. Failure Classification (VAL-EXP-010)

Per the contract checklist:

- muxer: **No.** ffmpeg output muxer succeeded, file is a structurally valid MP4 that ffprobe parses cleanly.
- ffprobe / playback: **No.** ffprobe walked all frames without error; this is the diagnostic, not the defect.
- timestamps: **Yes (root).** PTS spacing in the exported file is 90 000 ticks @ 90 000 tbn → 1 s per frame, instead of 1500 ticks (1/60 s).
- duplicate frames: **No.** `duplicatedPtsCount: 0`; frames carry distinct sizes (29 973/29 973/6 999/…) — they are distinct pictures.
- cadence: **Yes (gate dimension).** Mean/p95/p99 all 1000.000 ms vs nominal 16.667 ms.
- duration: **Partial.** Export self-reports 30 s window and walks 30 distinct PTS points 1 s apart; the cadence gate captures this.
- corruption: **No.** SHA256 matches helper/runner; file opens; no AVERROR.
- cleanup: **No.** post-run `pgrep cove-replay-engine`/`pgrep ffmpeg` both return zero; nvidia-smi back to idle.
- validation-only: **No.** Thresholds are unchanged from previous reruns (mean ±0.5 %, p95 ±2 %, p99 ±5 %, frame count ±1). The observation (30 frames vs 1800) is an order-of-magnitude miss that no reasonable threshold would absorb.

**Conclusion:** the defect is a real timestamp/cadence defect in the exported fMP4 pipeline (sample durations / frame production rate), surfaced for the first time now that the muxer and trun fixes let VAL-EXP-010 actually inspect a produced file. It is **not** caused by the muxer patch under verification — the muxer patch only added `-f mp4` to the ffmpeg argv and does not change sample timing.

Recommended action: file a new high-severity issue under `owner_on_fail = export` for "VAL-EXP-010: exported fMP4 carries 1 fps sample cadence (frame count and durations 60× off nominal)". Do **not** patch in this ticket.
